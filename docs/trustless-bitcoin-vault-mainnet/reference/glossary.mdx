---
title: Glossary
---

Protocol-specific terms used across the TBV documentation. Definitions reflect current mainnet behavior.

**AaveAdapter** — The user entry point for the Aave v4 application. It activates BTC Vaults as collateral, and exposes borrowing, repayment, collateral management (including `reorderVaults` and `withdrawCollaterals`), and liquidation against the Aave spoke.

**AaveAdapterPositionProxy** — A per-depositor proxy contract that holds one isolated lending position for that depositor on the Aave spoke, keeping each depositor's collateral and debt separated.

**AllowListPolicy** — The contract that gates peg-in submissions to allow-listed depositor addresses per application. It holds no usage state; only the admin writes the list. Used to enforce the allowlisted beta.

**Application** — A full integration registered in the `ApplicationRegistry` that implements `IApplicationEntryPoint` (its `activateVault(...)` callback) and receives vaults as they activate. The Aave v4 integration (`AaveAdapter`) is the first live application. Contrast with a **Resolver**, which extends an existing application rather than being a standalone one.

**Application Vault Keeper (AVK)** — A per-application operator that keeps an application's positions healthy; in the Aave application it acts as the arbitrageur during liquidation. Together with the Vault Provider it forms the application-scoped "Vault Keeper" set (distinct from the protocol-level Universal Challenger).

**ApplicationRegistry** — The protocol contract that manages application registration and each application's immutable vault keepers.

**BABE** — The cryptographic construction that makes verifying succinct proofs on Bitcoin roughly 1000x cheaper, combining witness encryption with garbled Groth16 verification, integrated with WOTS and a malicious-setup cut-and-choose flow. See **Research papers**.

**BTC Vault (BTCVault)** — The core primitive: native BTC locked on Bitcoin and represented on Ethereum so it can be used as collateral in an application, backed by a pre-signed Bitcoin transaction graph and depositor self-recovery paths. Managed on-chain by the `BTCVaultRegistry`.

**BTCVaultRegistry** — The core vault lifecycle manager. Handles Vault Provider registration, peg-in submission, ACK collection, Bitcoin inclusion-proof verification, activation, and redemption. Depositors activate via `activateVaultWithSecret(...)` (or `activateVaultWithSecretAndRedeem(...)`).

**BTCVaultSwap** — The default Liquidation Liquidity Provider (LLP) for the Aave application, backed by a WBTC spoke. It supplies liquidity during liquidation and is registered to the adapter via `registerLLP(...)`. See **LLP**.

**CapPolicy** — The contract that enforces on-chain exposure caps and tracks usage: `totalCapBTC` (total BTC per application) and `perAddressCapBTC` (per address). A `0` value means that cap is unlimited.

**Fairness payment** — In a liquidation that seizes slightly more collateral than needed, the surplus value is returned to the borrower as a fairness payment, so over-seizure of a whole-vault prefix does not penalize the borrower.

**FeeEscrow** — The protocol contract that manages protocol-level fees with escrow and pull-based claiming.

**Groth16** — The succinct proof system that TBV's proofs are wrapped to for on-chain verification; the SP1 zkVM proof is wrapped to Groth16. See **SP1**.

**Health factor** — The Aave-side measure of a position's collateralization. When it falls below the liquidation threshold the position becomes liquidatable.

**LLP (Liquidation Liquidity Provider)** — A contract that provides the liquidity used to settle a liquidation. `BTCVaultSwap` is the default LLP; additional LLPs can be registered via `registerLLP(...)` and used through `liquidateWithLLP(...)`.

**Partial-position liquidation** — TBV's liquidation model. Rather than seizing the entire position, the protocol seizes the minimum whole-vault prefix needed to restore the Aave spoke's target health factor; any over-seizure surplus is returned via the fairness mechanism.

**Peg-in** — Locking native BTC into a BTC Vault so it can be used as collateral on Ethereum. Bounded by `pegInAckTimeout` (off-chain setup ACK window) and `pegInActivationTimeout` (secret-reveal / activation window).

**Peg-out** — Redeeming a vault to unlock the underlying BTC back on Bitcoin.

**PositionAccount** — A dedicated per-owner account holding one delegated position. In the borrow-delegation resolver, `BorrowDelegationPositionAccount` holds one Aave position for a specific owner, who can grant verified delegatees per-reserve borrow allowances.

**Pre-PegIn HTLC** — The hash-time-locked Bitcoin output (a pre-pegin transaction output with a hashlock) that funds a peg-in. It is what lets a depositor self-refund on Bitcoin if setup or activation does not complete.

**ProtocolParams** — The contract holding protocol-wide parameters, including `maxPegInAmount` (per-vault peg-in maximum), `minimumPegInAmount`, `pegInAckTimeout`, `pegInActivationTimeout`, fee rates, Bitcoin timing parameters, Universal Challenger keys, Security Council keys, and `councilQuorum`. Parameters are versioned.

**Resolver** — A primitive that extends an existing application (rather than registering as a new one). The `BorrowDelegationResolver` extends the Aave adapter, resolving each depositor to exactly one deterministic `PositionAccount`. Contrast with an **Application**.

**Security Council** — A transitional, quorum-based body (`councilQuorum`) that can invoke an emergency pause during the beta. It cannot pay itself out; its role is a safety brake, not custody.

**SP1** — The zkVM used to generate the protocol's execution proofs, which are then wrapped to Groth16 for on-chain verification. Together the SP1 + Groth16 pipeline forms TBV's proving stack.

**Target health factor** — The health factor a liquidation aims to restore the position to (the Aave spoke's configured `targetHealthFactor`). It determines how much collateral a partial-position liquidation seizes.

**Universal Challenger** — A protocol-level operator that monitors for fraud across the whole protocol and challenges invalid state. It is separate from the application-scoped Vault Keeper roles.

**vaultBTC (VaultBTC)** — An 8-decimal, non-transferable, non-wrapped internal accounting token that represents locked BTC inside an application. It is minted just-in-time when a vault is added as collateral and burned when the vault is released.

**Vault Provider** — An operator that participates in vault setup and redemption (registering with a Bitcoin proof of possession and taking part in the pre-signed transaction graph). Part of the application-scoped Vault Keeper set.

**WOTS** — Winternitz one-time signature. The one-time signature commitments depositors and operators bind to, used in the pre-signed transaction graph, self-claim, and the BABE construction.
