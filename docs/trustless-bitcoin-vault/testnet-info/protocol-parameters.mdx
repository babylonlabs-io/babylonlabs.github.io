# Protocol parameters

This page lists the live parameter values for the current Babylon Trustless Bitcoin Vaults (TBV) public testnet release.

## Participant cheat sheet

Use these values while planning a public-testnet run:

| What you are checking | Current value |
| --- | --- |
| Minimum vault size | 0.01 BTC |
| Maximum vault size | 0.4 BTC |
| Maximum BTC per position | 0.4 BTC |
| Maximum vaults per position | 10 |
| BTC confirmations before setup can complete | 12 signet blocks |
| Peg-in ACK timeout | ~4 days |
| Activation timeout | ~6 days |
| Refund timelock | ~14 days (2016 BTC blocks) for the current parameter version. Vaults created under the earlier version use 577 BTC blocks (~4 days). |
| Redemption challenge window | ~3 days (432 BTC blocks) |
| BTC collateral factor | 78% |
| Liquidation threshold | Health factor below 1.0 |
| Borrowed assets per position | 1 at a time |

## Vault and position size limits

The public testnet enforces conservative limits on individual vaults, positions, and total application exposure. These limits apply on the current public testnet release and are expected to grow as the protocol matures.

| Parameter | Value | Description |
| --- | --- | --- |
| `minimumPegInAmount` | 0.01 BTC | Minimum BTC accepted for a single vault |
| `maxPegInAmount` | 0.4 BTC | Maximum BTC accepted for a single vault |
| `maxPositionBTC` | 0.4 BTC | Maximum total BTC across all vaults in one position |
| `maxVaultsPerPosition` | 10 | Maximum number of vaults in one position |
| `MAX_USER_RESERVES_LIMIT` | 1 | A position borrows from one reserve at a time. Borrowing a different asset reverts until the existing debt is repaid in full. |
| `maxHtlcOutputCount` | 10 | Maximum HTLC outputs in a batched Pre-PegIn transaction (enables multi-vault peg-in in one Bitcoin tx) |

## Application caps (CapPolicy)

Per-application and per-address BTC exposure limits enforced by the `CapPolicy` contract at vault activation. These Testnet limits will grow as the protocol matures.

| Parameter | Value | Description |
| --- | --- | --- |
| `totalCapBTC` (Aave app) | 10 BTC | Maximum total BTC across all users for the Aave v4 application |
| `perAddressCapBTC` (Aave app) | 0.4 BTC | Maximum BTC per address for the Aave v4 application |

## Peg-in timing

Two distinct timeouts govern the peg-in flow. The activation timeout always exceeds the ACK timeout so the depositor has a window to reveal the activation secret after off-chain setup completes. The versioned `tRefund` value comes from `getLatestOffchainParams()` on the [ProtocolParams contract](./contract-addresses.mdx). Existing vaults retain the parameter version active at creation. The vault's `offchainParamsVersion` identifies that version.

| Parameter | Value | Description |
| --- | --- | --- |
| `minPrepeginDepth` | 12 BTC blocks (signet) | Bitcoin confirmations required before ACK signers will sign the Pre-PegIn. |
| `pegInAckTimeout` | 28800 Ethereum blocks (~4 days) | Window for all required ACKs to be submitted (off-chain setup completion). If exceeded, the vault expires and the peg-in fee is refunded. |
| `pegInActivationTimeout` | 43200 Ethereum blocks (~6 days) | Window from vault creation for the depositor to call `activateVaultWithSecret`. Must exceed `pegInAckTimeout`. If exceeded, the depositor can refund via the Pre-PegIn refund leaf. |
| `tRefund` | 2016 BTC blocks (~14 days) | Current Pre-PegIn refund timelock. The value is relative, uses `OP_CHECKSEQUENCEVERIFY` from Pre-PegIn confirmation, and can differ for older vaults. |

## Redemption timelocks

Timelock parameters governing the claim, assert, and challenge windows during peg-out. The total wait from a successful claim to BTC payout is approximately three days, dominated by the challenge window.

| Parameter | Value | Description |
| --- | --- | --- |
| `timelockAssert` | 432 BTC blocks (~3 days) | Challenge window: time for a committed Vault Keeper, including a Universal Challenger or App Keeper, or the depositor to broadcast a `ChallengeAssert` after the claim is posted. |
| `timelockChallengeAssert` | 108 BTC blocks (~18 hours) | Claimer's disprove window: time for the claimer to broadcast a `WronglyChallenged` transaction after a challenge is raised. |

## Liquidation parameters

Thresholds used by the Aave v4 integration to determine when a position is liquidatable and how large the liquidator bonus is. Each liquidation seizes the position's head vault, so the amount seized is set by that vault's BTC amount rather than by a post-liquidation health target.

| Parameter | Value | Description |
| --- | --- | --- |
| `collateralFactor` | 7800 BPS (78%) | Fraction of BTC collateral value counted toward borrowing capacity |
| `liquidationThreshold` | 10000 BPS (1.0) | Health factor below which a position becomes liquidatable |
| `maxLiquidationBonus` | 10555 BPS (5.55% bonus) | Maximum bonus granted to the liquidator, applied at or below `healthFactorForMaxBonus` |
| `healthFactorForMaxBonus` | 0.9e18 WAD (0.9) | Health factor at or below which the max bonus applies |
| `liquidationBonusFactor` | 9000 BPS (90%) | Share of the max bonus paid when the health factor first drops below 1.0. On the current configuration the bonus starts at about 5.0% just below 1.0 and rises linearly to 5.55% at a health factor of 0.9. |
| `targetHealthFactor` | 1.0e18 WAD | Set on the Spoke but not used by this integration: liquidation size is determined by the head vault, not by a target health factor. |
| `liquidationFee` | 0 BPS | Structurally zero for BTC collateral. UTXOs cannot be partially extracted, so an Aave-style liquidation fee cannot be applied. |

## Off-chain coordination parameters

| Parameter | Value | Description |
| --- | --- | --- |
| `babeTotalInstances` | 307 | Total garbled circuit instances generated in the BABE cut-and-choose protocol at peg-in |
| `babeInstancesToFinalize` | 6 | GC instances retained after the cut-and-choose; used during dispute resolution. The remaining 301 are revealed to verify honest construction. |
| `proverCircuitVersion` | 1 | SP1 prover program (ELF) version; monotonic. |
| `feeRate` | 2 sat/vB | Bitcoin transaction fee rate used by the protocol on the public testnet. Mainnet values would be higher. |
| `minPeginFeeRate` | 20 sat/vB | Minimum PegIn transaction fee rate enforced by ACK signers. |

| Parameter | Value | Description |
| --- | --- | --- |
| `councilQuorum` | 3 of 5 (public testnet) | Required signatures for council action (such as `CouncilNoPayout` emergency intervention). |

## Vault Provider commission

Each Vault Provider sets its own commission per vault, taken in BTC from the redemption payout. The commission rate is fixed in the pre-signed Payout transactions at vault creation and cannot change for that vault.

## Collateral record

| Parameter | Value | Description |
| --- | --- | --- |
| `name` | Native BTC | On-chain ERC-20 name of the collateral record (`vaultBTC` contract) |
| `symbol` | `BTC` | On-chain ERC-20 symbol of the collateral record (internal accounting) |
| `decimals` | 8 | Matches Bitcoin's satoshi precision (1 unit = 1 BTC = 100,000,000 satoshis) |
| Transfer restrictions | Restricted to the Aave v4 integration | The collateral record is not freely transferable. It exists only as an internal accounting unit within the Aave Adapter. |
